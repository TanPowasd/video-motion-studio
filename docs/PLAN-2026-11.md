## 1. 远程高并发推送修复

背景：[REMOTE-STRESS.md](REMOTE-STRESS.md) 测得约 10 个高频编辑者稳定；≥50 时几乎所有 push 返回 `REVISION_CONFLICT`（并非真实内容冲突），形成活锁。

计划：

1. **服务端自动变基**：push 遇到 revision 落后时，在协调锁内基于最新快照重新三路合并；合并干净就直接提交，只有真实冲突才返回 `REMOTE_CONFLICT`。整个 push（重载、合并、校验、提交）放在同一个锁区间内，去掉锁外窗口。
2. **pull 读内存快照**：pull / status 直接读协调进程内存中的已提交快照；`reload()` 先比较原始文本，再按文件内容哈希缓存解析结果，未变化的文件不再全量 schema 解析。
3. **presence 广播节流**：只在可见变化时广播，合并到约 250 ms 一次；一次序列化共享给所有 SSE 连接；写入遵守背压；`MAX_PEERS` 改为按最近活跃时间的真正 LRU 淘汰。
4. **客户端退避**：仍然冲突时客户端按指数退避加随机抖动重试。
5. 次要：每次 push 只做一次完整校验；历史写入不阻塞响应路径（顺序仍保证）。

验收（本地可复现）：

```bash
npm run stress:remote -- --clients 10,50,100 --duration 20 --scenario mixed
```

- 50 客机：不同节点编辑者被拒率 < 5%，提交吞吐 ≥ 10/秒，不再塌到 1/秒以下。
- 同属性冲突仍正确返回 `REMOTE_CONFLICT` 并暂存冲突，不丢更新。
- 每档终态所有客机 revision 与主机一致，`vmotion validate` 通过。
- 结果更新到 `REMOTE-STRESS.md` 与 `remote-stress-results.json`（标注修复前后）。

## 2. 版本历史分支与合并

背景：`.vmotion/history/` 现为单主线（log / show / diff / checkout / revert）。

计划：

- 引用：`.vmotion/history/refs/heads/<分支>`，`HEAD` 指向当前分支；默认分支 `main`，旧工程自动迁移，不改已有提交哈希。
- 操作：创建、列出、切换、重命名、删除分支（删除未合并分支需 `--force`）；`merge <分支>` 以最近公共祖先做稳定 ID 三路合并（沿用 `mergeJson` / `mergeText`），干净时生成双父合并提交，冲突时写入现有冲突暂存区并提示逐项解决，可 `merge --abort`。
- 切换分支前若工作区有未提交改动则拒绝（`--force` 才丢弃），避免静默覆盖。
- 远程：客户端可指定推送到的分支；协调节点按分支各自维护 revision，主线行为不变。
- 入口：CLI `vmotion history branch|switch|merge`、`vmotion remote branch|switch|merge`；MCP `project_history` 增加 `branches / branch_create / branch_switch / branch_delete / merge` 动作；全部支持 `mode:"plan"` 预演。

验收：

```bash
npx vitest run tests/version-history.test.ts tests/version-branches.test.ts
vmotion history branch try-color && vmotion history switch try-color
# 改动并提交后
vmotion history switch main && vmotion history merge try-color
vmotion history log --graph
```

- 分叉后两边改不同节点 → 干净合并，一次撤销可回退。
- 两边改同一属性 → 冲突暂存，解决后提交；`merge --abort` 恢复到合并前。
- 旧单主线工程打开后历史完整、`log` 输出不变。

## 3. 编辑器「版本历史」面板

计划：在编辑器加入「版本历史」入口（本地工程与远程连接都可用，远程时读协调节点历史）：

- 提交列表：时间、作者/peer（人 = 珊瑚色，AI = 薄荷色）、说明、改动文件数；按分支筛选，显示合并点。
- 查看提交：改动文件与 JSON / 文本差异，可选显示该提交的预览帧。
- 操作：检出到某提交（预览后确认）、回滚某提交、创建 / 切换 / 合并 / 删除分支；合并冲突在面板内逐项选择保留哪一边。
- 所有写操作走预检 + 确认，与现有撤销记录一致；中文界面，沿用现有配色，不模仿 VS Code。

验收：`npm run build` 后打开示例工程 → 版本历史 → 新建分支、改动、切回 main、合并；冲突场景能在面板内解决；远程连接到 `vmotion remote serve` 时面板显示远程历史。

## 4. Windows 安装包与升级

背景：目前只有可复制的便携 ZIP（`scripts/package.ts` + `portable-zip.ps1`）。

计划：

- 新增 NSIS 安装包 `Vmotion-Setup-<版本>-x64.exe`：默认按用户安装（不需要管理员），可选安装目录；开始菜单与桌面快捷方式；注册 `.vmotion` 工程关联（可选）；`vmotion` CLI 可选加入用户 PATH。
- 升级：覆盖安装保留设置、最近项目与 profile；启动时检测版本变化并做一次性迁移。
- 卸载：移除程序文件与快捷方式，**保留**用户工程、素材和 profile（卸载器里可勾选一并删除 profile）。
- 便携 ZIP 保持不变，两者共用同一套运行时、许可与源码清单。
- 命令：`npm run package:installer`；Windows CI 额外上传安装包 artifact。

验收（维护者 Win11 本地）：

1. 运行安装包 → 开始菜单启动 → 新建工程、导出一段视频。
2. 安装新版本覆盖旧版本 → 最近项目和设置仍在。
3. 卸载 → 程序目录删除，工程文件仍在；重新安装后可直接打开。
4. 安装后 `vmotion --version` 与 MCP 连接正常。
